核心结论：流程架构是"完整"的，但存在"配置型组件"问题

系统从需求拆解 → 规划 → 写作 → 质量门 → 人设约束的全流程设计合理，韧性机制（降级/重试/原子写）是亮点。但本次审计发现：21 个初始化组件中，生成主链路实际只使用约 7 个——1 个完全死代码（Embellisher），1 个初始化后从未被调用（ConsistencyValidator，且 engine 文档注释宣称它在主管线中）。这是典型的"组件被创建了，但没有生效路径"问题：系统像一台装配了 21 个零件的机器，但只有 7 个零件真正参与加工。客户需求匹配度方面，流程覆盖完整，质量稳定性不足（实测 60-70 分区间，缺反馈闭环与效果度量）。

✅ 全流程覆盖 ✅ 韧性设计突出 ⚠️ 14/21 组件不在主链路 ⚠️ 文档宣称与实际管线脱节 ⚠️ 无质量反馈闭环

2设计合理性评估

分三个层次：架构层合理 ✓ / 组件层有问题 ⚠ / 治理层缺失 ✗

✅ 架构层：合理

  • 分层单向依赖：API → Engine → Agent → 记忆 → LLM，依赖方向干净（重构后）
  • 韧性设计是亮点：四级 JSON 降级、重试退避、断线续传、原子写、僵尸锁兜底
  • 记忆分层正确：L1 设定 / L2 近期上下文 / L3 伏笔，摘要渐进压缩控制膨胀
  • 新增能力成本低：人设蒸馏今天从想法到上线约 2 小时（Mixin + Router + 前端）

⚠️ 组件层：存在"配置型组件"

  • Embellisher 完全死代码：初始化但全库零调用点，还挂在 docstring 的 Support 列表里
  • ConsistencyValidator 未生效：engine docstring 宣称 "Planner → Writer → ConsistencyValidator → OpeningOptimizer → TwistDesigner" 管线，实际主线从未调用它——文档与代码脱节
  • 双轨生成未收敛：普通/原子两套实现并存，各自调参，质量差异未度量
  • 开局/反转等组件只在端点级生效：主动分析能力没有反哺生成

❌ 治理层：效果不可度量

  • 无模块级度量：每个 Agent 的触发率/改善率/失败率没有指标——无法回答"质量门重写真的变好了吗"
  • 无反馈闭环：用户无法标记"这章写得好/差"，系统不会学习偏好（AUDIT P2-1）
  • 质量基线缺失：只有 AUDIT 一次性抽样（60-70 分），没有持续采样
  • 测试只测"能跑"不测"效果"：99 个测试验证模块行为，不验证生成质量

客户需求系统对应能力匹配评估

需求匹配结论

流程需求全部覆盖（8/9），唯一硬缺口是反馈闭环。但"覆盖"不等于"有效"——质量门、状态追踪、一致性校验三个环节处于"有组件但效果未验证"状态，真实客户感受到的质量 = 主链路上 7 个组件叠加的结果，而非 21 个组件宣称的能力。

4怎样确保每个模块都起到预期效果

三层保障机制：链路审计（发现问题）→ 行为测试（验证机制）→ 效果度量（量化贡献）。

第 1 层 · 调用链审计（已有基础，需制度化）

  • 本报告已做一次全量审计：21 组件 × 主链路调用点
  • 立即可做：把"模块调用审计"做成 CI 检查——每个初始化组件必须有调用点，否则报警（防止再出现 Embellisher 式死代码）
  • 修正 engine docstring 与实际管线不一致（ConsistencyValidator 要么激活、要么从文档移除）
  • 激活或移除：ConsistencyValidator 建议激活到章节生成后（它 708 行代码不是白写的），Embellisher 建议移除或并入 Humanizer

第 2 层 · 行为测试（机制存在且正确）

  • 现有 99 个测试覆盖"模块行为正确"，但**不覆盖"模块在主管线中被正确触发"**
  • 新增集成测试：mock LLM 跑完整生成链路，断言每个主链路组件的调用次数与输入输出（如"质量门 score<40 时必须触发 writer 重写"）
  • 为双轨生成加"产出对比测试"：同一章节普通/原子各生成 3 次，比较连贯性/多样性指标——数据驱动收敛决策

第 3 层 · 效果度量（每个模块的贡献可量化）

  • 模块度量埋点：每个 Agent 调用时记录 {触发次数, 输入分, 输出分, 耗时, 失败率}——quality gate 重写前后分数、Humanizer 前后 AI 检测分、人设约束注入前后的一致性评分
  • 质量采样器：每生成 5 章自动跑一次 8 维评估（EvaluationSystem 已有！），日志记录质量趋势
  • 仪表板：把 quality-dashboard API 扩展为"模块健康度"（哪个模块在干活、干得好不好）
  • 核心判据：任何模块连续 N 次"零触发"或"零改善"→ 自动告警

5生成质量提升路径

基于审计结论的五个抓手，按投入产出排序。

抓手 1 · 主链路补强（投入小，见效快）

  • 激活 ConsistencyValidator：章节生成后跑一致性校验，发现问题注入下一章修正指令（AUDIT P2-2 的路径，代码现成）
  • 质量门阈值校准：Humanizer 跳过阈值 50 → 70（AUDIT P1-2），重写接受条件从 "+5 分"改为 "+10 分或绝对分 ≥60"
  • 删除 Embellisher（或并入 Humanizer 管线），消除死代码认知负担

抓手 2 · 反馈闭环（需求缺口，客户价值最高）

  • 每章加 👍👎 + 一句话理由（前端 + API，工作量半天）
  • 反馈数据落 SQLite → 形成"偏好档案"（用户喜欢快节奏/细腻描写/少对话）
  • 偏好注入 Writer system prompt 与质量门权重——系统开始"越写越懂你"

抓手 3 · 上下文预算管理（AUDIT P0-3，长篇小说瓶颈）

  • 当前 7 层上下文到 50 章可能超 12,000 字符，挤占生成空间
  • 实现分级截断：L1 全量保留，L2-L4 按章节号动态压缩，保证 ≥60% token 留给生成
  • 人设约束段控制在 600 字内（当前实现已限 120 字/条 × 约 15 条）

抓手 4 · 人设蒸馏深化（今天上线的能力，值得吃透）

  • 创建小说时自动蒸馏主角 + 前 3 配角（创建流程串行调用，+30s）
  • 人设卡增加"关系行为模式"（对林墨 vs 对陌生人 vs 对敌人的行为差异）
  • 防崩校验规则接入质量门：生成后检查是否违反角色反模式（如"顾尘长篇大论讲道理"）

抓手 5 · 双轨收敛与 A/B（消除质量方差）

  • 用效果度量数据（抓手 3 第 2 层测试）决定保留普通路径还是原子路径
  • 或引入 A/B：每章两版都生成，质量门选优（AUDIT P0-2 建议），用户可切换
  • 收敛后单一管线，调参成本减半
