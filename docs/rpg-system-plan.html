1. 需求解读

目标：在现有 NovelGenerator App 内新增"角色扮演"子页面，用户与小说角色（或独立养成角色）进行多轮对话，系统通过对话持续更新角色卡，形成养成闭环。

三个核心关键词：

① 对话收集 — 多轮聊天界面，流式输出（复用现有 SSE 基建）；
② 角色卡更新 — 从对话中提炼"角色的了解、关系、性格发现"，增量写回角色卡；
③ 养成 — 亲密度数值化 + 关系阶段升级 + 记忆沉淀，让角色"越聊越懂你、越聊越熟"。

区别于小说写作：写作是"单向生成长文本"，扮演是"双向多轮对话 + 玩家输入驱动角色状态变化"。这是全新的交互范式，但底层 LLM 管线、记忆层、角色一致性资产均可复用。

3. 总体架构设计

角色来源（两条路）

A. 从小说导入（主推）
书架选一本小说 → 从 character_bible 选角色 → 自动生成角色卡。
继承已有设定/声音/关系，与写作共用世界观。

B. 独立养成角色
不依赖小说，创建时填 1 句话设定 → 蒸馏出角色卡。
v1 仅做方案 A，B 留 v2。

对话上下文组装（成本控制）

角色卡+ 声音卡+ 关系摘要+ 最近 12 轮

固定 ≈ 3-4k tokens/轮，成本可控。
每 50 轮触发一次摘要压缩（复用 Summarizer），旧对话归档。

4. 数据模型（角色卡）

character_rpg.json（每角色一份，增量更新，永不覆盖已有信息）
{
  "character": { "name": "苏晚", "source": "novel:夜火", "base_identity": "…来自bible" },
  "intimacy": {                    // 亲密度养成
    "value": 42,                    // 0-100
    "stage": "熟悉",                 // 陌生→相识→熟悉→亲密→特殊
    "history": [ {"at": "2026-08-02", "delta": +6, "why": "她主动讲了自己的过去"} ]
  },
  "discovered": [                    // 性格发现（对话中提炼）
    { "trait": "外冷内热，害怕辜负", "evidence": "对话#23" }
  ],
  "relationship": { "label": "重逢旧识", "notes": "她记得你十年前的习惯" },
  "memories": [                     // 记忆沉淀
    { "id": "m12", "what": "她讨厌下雨天", "from": "chat#45", "recallable": true }
  ],
  "milestones": [ "初次对话", "分享秘密" ],
  "meta": { "chat_count": 47, "last_updated": "…", "version": 12 }
}

设计原则：base_identity 来自小说设定（不可变）；discovered / memories / intimacy 全部来自对话证据（可追溯、可回溯）。养成 = 证据驱动的增量累积，不是随机数值。

5. 养成机制设计

5.1 亲密度数值模型

阶段数值区间解锁内容升级触发（示例规则）
🤝 陌生0-20基础闲聊完成 5 轮对话
👋 相识21-45角色主动提问用户分享个人信息 / 角色透露一个偏好
❤️ 熟悉46-70记忆回溯（可引用早期对话）角色主动讲述往事 / 用户表达关心
💞 亲密71-90秘密解锁、专属称呼角色分享秘密 / 共同经历事件
⭐ 特殊91-100自定义关系标签、彩蛋长期陪伴（≥300轮）+ 深度事件

数值更新由 LLM 判定 + 规则兜底：每轮对话后，养成判定器输出 {delta, reason}（LLM 给建议值，规则层 clamp 到 [-2, +8]/轮，防止刷屏刷数值）。

5.2 角色卡更新管线（核心创新点）

用户对话→ 写入 chat_logs.jsonl→ 累积 ≥10 轮 or 手动刷新→ CardUpdater（LLM）→ 增量合并角色卡→ 返回"角色卡已更新"通知
  • 触发方式：自动（每 10 轮，后台异步，不阻塞聊天）+ 手动（角色卡面板"刷新"按钮）
  • 更新内容：新发现的性格特质、记忆点、关系变化、亲密度判定依据
  • 一致性保证：更新 prompt 只输出"变化"，合并器负责增量 merge；已存在的 trait 不覆盖只补充 evidence
  • 复用：更新管线 = CharacterStateTracker 的"读文本→提取 JSON→合并"模式的对话版

5.3 扮演一致性（防角色漂移）

约束层机制来源
口吻层声音卡注入系统 prompt（语气/习惯用语/禁忌词）CharacterVoices 复用
人格层角色卡 base_identity + discovered traits新建 + bible 复用
记忆层memories 可被角色主动 recall（"你还记得…"）新建
扮演规则层系统 prompt 强制：永远以角色第一人称，不替用户做决定，不跳出扮演新建（对话专用 prompt）

6. 对话流与更新管线

6.1 单轮对话时序

用户发送 → POST /api/rpg/chat
         ├─ 1. 追加用户消息到 chat_logs.jsonl
         ├─ 2. 组装上下文（角色卡+声音卡+摘要+最近12轮）
         ├─ 3. LLM 流式生成（resilient_client，SSE 推送）
         ├─ 4. 流结束后追加角色回复到 jsonl
         └─ 5. 后台任务（不阻塞）：
              a. 养成判定器 → 亲密度 delta（LLM+规则）
              b. 若对话数 %10==0 → CardUpdater 更新角色卡
              c. 里程碑检测（首次/秘密/冲突等）

6.2 关键 API 设计

端点说明
GET /api/rpg/novels/{id}/characters可扮演角色列表（bible 角色 + 已有角色卡）
POST /api/rpg/{novel}/{char}/chat发送消息，SSE 流式返回角色回复
GET /api/rpg/{novel}/{char}/card角色卡详情（含亲密度/阶段/记忆/里程碑）
POST /api/rpg/{novel}/{char}/refresh手动触发角色卡更新（返回 diff 预览）
POST /api/rpg/{novel}/{char}/reset重置养成（保留 base_identity）
GET /api/rpg/{novel}/{char}/history历史对话分页（jsonl 读取）

8. 里程碑与工作量

M1 — 跑通对话（0.5-1 人日）

rpg.py 最小路由 + chat 端点 + 前端聊天 UI + 上下文组装（角色卡最小版）。验收：能选角色、能流式对话、对话落盘。

M2 — 养成闭环（1.5-2 人日）

角色卡完整数据结构 + 养成判定器（亲密度/阶段/里程碑）+ CardUpdater 增量管线 + 角色卡面板 UI。验收：聊 10 轮后角色卡出现变化，亲密度进度可见。

M3 — 记忆与打磨（1-1.5 人日）

对话摘要压缩 + 记忆回溯（角色主动 recall）+ 重置/导出 + 移动端适配 + 测试回归 + 打包发版。

总工作量约 3-4.5 人日（按全栈 1 人计算），其中 60% 是新增对话/养成领域，40% 是复用资产接线。

9. 风险与对策

风险说明对策
上下文膨胀对话无限累积，token 成本线性上涨12 轮窗口 + 每 50 轮摘要压缩（Summarizer 复用）；上限 4k tokens/轮
角色漂移聊久了性格走样四层约束（声音卡/角色卡/记忆/扮演规则）；CardUpdater 只增量不覆盖
养成数值失衡刷屏刷亲密度 / 判定不合理LLM 建议 + 规则 clamp（-2~+8/轮）；阶段升级需多维度条件，非纯数值
对话安全用户诱导角色输出越界内容对话系统 prompt 内置角色人格护栏（不脱离人设）；复用成熟题材尺度方案
数据量jsonl 无限增长50 轮摘要归档后原文截断保留最近 200 轮；提供导出/清理
多小说多角色文件分散统一 novels/{id}/rpg/ 目录，SharedMemory 记忆类型注册

11. 语音能力评估（追加 2026-08-02）

结论：有，且已实测通过 —— edge-tts 完全免费（零注册、零 API Key、无字符限制）。

基于微软 Azure 神经语音引擎（Edge 浏览器同款），中文 10+ 音色，支持 语速 rate + 音调 pitch 定制 —— 同一音色调 pitch 就能做出多个"角色声线"，正好满足角色扮演的差异化需求。

方案成本评估
edge-tts（主方案）0 元，无 key 无注册实测：3 个差异化角色音色全部 1.5s 生成成功（52/38/34KB mp3）；偶发限速/网络抖动，加 2s 退避重试即稳；需联网
Web Speech API（兜底）0 元Android WebView 内置系统 TTS，edge-tts 不可用时自动降级；音色单一（系统默认）
CosyVoice / Fish Audio（v2 可选）本地部署免费 / 注册送额度音色克隆：3 秒音频样本即可克隆专属声线，角色音色独一无二；需 GPU 或注册
云服务（火山/讯飞/MiniMax）免费额度（数千-数万字符）质量高但需实名注册，额度用尽即收费；不必要

集成设计（v1）

角色回复完成→ 角色卡 voice 配置(音色+语速+音调)→ edge-tts 生成 mp3→ 磁盘缓存（文本 hash）→ 前端播放

要点：① 角色卡增加 voice 字段（每个角色一套声线配置）；② 文本 hash 缓存，重复内容零成本；③ 失败 2 次自动降级 Web Speech API；④ 生成走后台线程，不阻塞聊天 UI。

成本核算：每轮回复语音 ≈ 0 元 + 40-80KB 流量。日均 50 轮对话 = 0 元。相比云 TTS（约 0.01-0.05 元/千字符），年省近千元。

12. 结论与建议

建议：做，且从 M1 直接做到 M2 再发版。理由：

① 复用率高（60%），3-4.5 人日即可出完整养成闭环，边际成本低；
② 与小说写作形成产品闭环——写好的角色可以"聊"，聊出来的关系可以反哺写作（角色卡 traits 可导出为写作参考），这是现有同类工具（如 Glow/星野）没有的差异化；
③ 架构上全部走既有模式（SSE/记忆层/状态提取管线），不引入新技术栈，风险低。

建议的取舍（v1 范围控制）：① 只做"从小说导入角色"，独立养成角色 v2 再上；② 亲密度分 5 阶段但升级规则先用规则兜底，LLM 判定持续调参；③ 秘密解锁/专属称呼这类"惊喜内容"放 M3，不阻塞主流程。
