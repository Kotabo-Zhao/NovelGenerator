## 1. 执行摘要

当前项目不是一个单纯的前端项目，而是以下几套能力叠加形成的复合系统：

```text
浏览器/PWA 单文件 Vue 页面
        ↓
FastAPI + 本地文件/SQLite 辅助存储
        ↓
多阶段大纲、节拍、写作、评估、记忆、互动、趋势、导出模块
        ↓
Android Chaquopy 壳（复制一套 backend/core 与 api）
```

它已经具备较完整的“从灵感到成稿”功能闭环，但产品层面存在两个根本矛盾：

1. **当前系统按单用户、本地文件目录、单进程工具设计；微信小程序上线需要用户身份、数据隔离、任务持久化和可恢复的云端服务。**
2. **当前页面按桌面/宽屏工作台设计；小程序需要移动端主流程，现有功能全部暴露会造成高认知负担。**

因此建议采用“后端安全与多租户重构 + 原生小程序核心闭环重建 + 高级能力分层迁移”的路线，而不是继续在现有 `web/index.html` 上叠加按钮或尝试直接打包成小程序。

### 上线阻断项（P0）

| 编号 | 阻断项 | 证据 | 影响 |
|---|---|---|---|
| P0-01 | 没有认证、授权与用户隔离 | 全仓未发现 `openid`、`unionid`、JWT、Bearer、session、user_id 等实现；`render.yaml` 也是单实例本地存储 | 任意调用方可能读取、修改或删除其他用户作品；不能作为公开服务 |
| P0-02 | 小说 ID 未在多数路由统一校验，文件路径直接拼接 | `backend/core/shared_memory.py:1240-1245`、`:1384-1385` 使用 `os.path.join(self.novels_dir, novel_id, ...)`；AST 统计 90 个路由仅 20 个调用验证 | 存在路径穿越/越权读写风险，且 Windows 路径分隔符使风险更应优先处理 |
| P0-03 | 没有原生微信小程序工程 | 没有 `app.json`、WXML、WXSS、原生小程序页面或微信登录实现；当前是 DOM/Vue/PWA | 不能直接提交为原生小程序；必须重建客户端或先采用受限的 `web-view` 过渡方案 |
| P0-04 | LLM 消耗、请求时长和输入规模没有形成服务端预算 | 写作实际 `max_tokens` 可到 12,000/24,000；原子化路径每章可能进行蓝图 + 5–7 beat × 3 候选等多次调用；请求体多处使用裸 `dict` | 恶意或误操作可造成高额 API 费用、线程/连接耗尽和长时间卡死 |
| P0-05 | 内容安全、隐私同意、数据生命周期与运营合规流程缺失 | 未发现内容审核、敏感词/模型审核门禁、隐私协议确认、用户注销/删除/导出授权流程 | 上线审核与运营风险高；需要在产品和服务端共同补齐 |

### 最高优先级 P1

1. `backend/api/routers/novels.py:399-403` 的 `_checkpoint_path()` 使用了未导入的 `config`。检查点读写异常被宽泛 `except` 吞掉，因此“批量断点续传”实际不可用。
2. `backend/api/server.py` 默认 `CORS_ORIGINS=*`，健康检查接口返回绝对存储路径和小说列表；公开环境下属于不必要的信息暴露。
3. 异步接口中仍有同步 LLM 调用和同步流式迭代；高并发下会阻塞事件循环，SSE 断线、重试、取消和后台任务状态也没有统一任务模型。
4. `web/index.html` 已约 328 KB、约 5,200 行，包含约 112 个按钮、201 个 `v-if`、93 个 `ref`、72 个 `fetch`；它与 backend/android 各有一份副本，继续改造会放大回归风险。
5. 生成质量链路有不少规则与自动补写，但上下文裁剪可能移除当前章节大纲；合规补写发生在部分质量评估之后，补写后的文本没有完整重新评估。

## 3. 当前架构盘点

### 3.1 目录和规模

| 区域 | 现状 | 主要问题 |
|---|---:|---|
| `backend` | 约 95 个文件、约 38,900 行 | 功能集中、模块之间耦合高，API 与本地文件实现边界不清晰 |
| `web` | 5 个文件，主页面约 328 KB、约 5,200 行 | 单文件 Vue，状态、请求、模板、样式和业务动作混在一起 |
| `android/app/src/main/python` | 约 86 个文件、约 37,345 行 | backend/core 与 api 的同步副本，易漂移 |
| `tests` | 26 个文件、约 5,076 行 | 以脚本/旧版逻辑测试为主，无法覆盖公开 API 的安全边界 |
| `backend/tests` | 5 个文件、约 1,149 行 | pytest 测试未纳入当前 CI 主路径 |

当前前端的三份 `index.html` 内容一致，说明同步暂时可控；但这是“复制一致”，不是“单一源码”。Android 同步工具是 backend → android 的单向复制，只报告 Android 多余文件，不负责删除，长期会产生漂移。

### 3.2 依赖和配置漂移

- 根 `requirements.txt` 使用 `pydantic>=2.0.0`，Android Gradle/Chaquopy 依赖使用 `pydantic 1.10.26`，FastAPI/OpenAI/uvicorn 版本也与根目录不同。
- `backend/requirements.txt` 没有显式声明 `python-dotenv`，但 `backend/config.py` 直接调用 `load_dotenv()`。
- `backend/config.py` 声明 `MAX_CONTEXT_TOKENS=8000`、`MAX_CHAPTER_TOKENS=4000`，但核心写作实现使用自己的动态上限；配置项与实际保护逻辑不一致。
- `.env.example` 默认 `CORS_ORIGINS=*`，适合本地快速启动，不适合公开服务。
- README、历史审计、项目状态和当前 HEAD 版本不一致，文档不能直接作为当前状态依据。

### 3.3 部署模型

`render.yaml` 以单个 Render Web Service 启动 FastAPI，使用 `/var/data` 持久盘，小说内容主要落在本地目录，没有数据库、消息队列或对象存储抽象。当前限流和生成并发控制也是进程内状态。

该模型可以支撑个人/单实例工具，但不能自然扩展到：

- 多用户资源隔离；
- 多实例部署和滚动发布；
- 生成任务跨进程恢复；
- 大文件导出和长期存储；
- 用户配额、计费、审计和运营数据统计。

## 4. 安全审计

### 4.1 P0：资源越权与路径穿越

`backend/api/deps.py` 中确实存在 `_validate_novel_id()`，但没有形成全局依赖。AST 统计结果如下：

| 路由模块 | 路由数量 | 明确调用小说 ID 校验的路由 |
|---|---:|---:|
| `characters.py` | 4 | 4 |
| `feedback.py` | 2 | 2 |
| `interactive.py` | 14 | 14 |
| `novels.py` | 19 | 0 |
| `outline.py` | 4 | 0 |
| `quality.py` | 11 | 0 |
| `requirements.py` | 6 | 0 |
| `storygraph.py` | 10 | 0 |
| 其他模块 | 20 | 0/未统一核验 |
| **合计** | **90** | **20** |

`SharedMemoryManager._get_path()` 和 `get_novel_dir()` 直接把 `novel_id` 拼到存储根目录下。只在删除接口内部做校验不能保护读取、写入、导出、质量面板、剧情图谱和角色档案等路径。

**整改要求：**

1. 小说主键改为服务端生成的 UUID/不可猜 ID，不把用户可控字符串当目录名。
2. 通过统一依赖在所有需要小说资源的路由前置校验身份、资源归属和 ID 格式。
3. 文件路径必须由安全的内部 ID 生成，并使用 `Path.resolve()` 验证最终路径仍在租户根目录内。
4. 对 `..`、斜杠、反斜杠、保留设备名、超长 ID 做测试；不能只靠黑名单。

### 4.2 P0：无认证、授权和租户隔离

项目没有微信登录换取会话的服务端实现，也没有资源 owner 字段。当前 `/api/health` 甚至会返回存储绝对路径、小说数量和小说目录信息；这对本地诊断有用，对公开服务不应默认开放。

**整改要求：**

- 小程序 `wx.login()` 换取服务端短期会话；服务端保存稳定内部 user_id，不在业务表中依赖 openid 明文展示。
- 所有小说、章节、任务、反馈、导出记录都带 owner_id，并在查询/修改/删除时强制校验。
- 健康检查仅返回服务状态，不返回绝对路径和作品清单；诊断信息只进受控日志。
- 认证、作品访问、生成任务、导出分别设置权限和审计事件。

### 4.3 P0/P1：输入、资源和 LLM 消耗未封顶

多处接口使用裸 `dict` 接收请求体，缺少统一的字段类型、长度、枚举和嵌套深度限制。小说需求、上下文、反馈和自定义风格都可能进入 prompt。

模型调用的消费边界也不统一：

- `Writer.write_stream()` 将 `safe_max_tokens` 设为 `min(target_words * 3, 12000)`；续写路径可到 24,000。
- 原子化章节先生成蓝图，再拆 5–7 个 beat，每个 beat 默认生成多个候选，随后还会做桥接、合规和质量处理。
- 重试、超时、取消、客户端断开后的资源回收没有统一任务预算。

**整改要求：**

- 用 Pydantic schema 覆盖所有请求体，限制文本长度、章节范围、候选数、总字数和上下文大小。
- 服务端按用户/日/作品/任务维护 token、金额、并发和超时预算。
- 所有 LLM 输出先按结构化 schema 解析，再进入文件、数据库或后续 prompt；不能把模型输出视为可信指令。
- 公开端点设置真实的分布式限流/配额；进程内 60 req/min 和 3 个生成并发只能作为单机兜底。
- 生成应转为持久化 job，HTTP 只创建/查询/取消任务，不让请求线程承担整本小说的生命周期。

### 4.4 P1：配置、错误和安全头

- CORS 默认通配符；正式环境必须配置明确的合法来源/小程序服务域名策略，并区分开发和生产配置。
- `android/app/src/main/AndroidManifest.xml` 设置 `usesCleartextTraffic=true`，虽然不是小程序客户端，但反映出发布配置仍偏开发态。
- 生产服务需要 HTTPS、HSTS、X-Content-Type-Options、Frame 防护、合理 CSP/错误响应策略；当前未见完整安全头基线。
- 异常日志和返回信息需要区分内部诊断与用户提示，不能把路径、堆栈或上游错误原样暴露。

### 4.5 内容与风格合规风险

`backend/core/styles.py` 中存在以具体作者姓名作为风格预设的内容。商业化产品应改成可解释的属性组合，例如“短句密度、叙事视角、节奏、对白比例、意象浓度”，并移除直接模仿在世作者的产品入口，同时增加用户输入、生成文本和分享内容的审核策略。

## 5. API 与工程质量审计

### 5.1 已确认的真实缺陷

#### P1-API-01：批量断点续传实际上失效

`backend/api/routers/novels.py:399-403` 使用 `config.NOVELS_DIR`，但该文件只导入了配置常量，没有导入 `config` 模块。保存、读取和清除检查点都捕获了宽泛异常，因此错误不会显性暴露，导致接口看似成功、恢复状态却始终丢失。

#### P1-API-02：重复导入/重复定义校验函数

`novels.py` 既从 `api.deps` 导入 `_validate_novel_id`，又在本文件重新定义同名函数，但多数路由没有调用它。这会给后续维护者造成“已经有校验”的错觉。

#### P1-API-03：创建失败后自动切换路径可能重复副作用

创建小说接口在同步引擎调用异常后再尝试流式流程；如果第一次调用已经部分创建目录、写入计划或消耗模型额度，第二次尝试可能重复副作用。应改为显式 job 状态与幂等键。

#### P1-API-04：大文件导出直接内嵌 JSON

批量导出接口将完整内容放入 JSON 响应，长篇小说会造成高内存、高带宽和小程序端解析压力。应生成带权限的临时下载对象或分块导出任务。

#### P1-API-05：测试辅助脚本自身不可用

`tests/health_check.py` 使用 `urllib.parse.quote()`，但只导入了 `urllib.request` 和 `urllib.error`，未明确导入 `urllib.parse`。这类健康检查脚本应修复并纳入 CI，或删除硬编码本地服务依赖。

### 5.2 CI 与可维护性

当前 CI 主要做语法扫描、敏感 key 扫描、同步检查和一个根测试文件；没有覆盖：

- 所有 90 个路由的认证/权限/路径测试；
- backend/tests 下的 pytest 测试；
- 真实 HTTP API 合约测试；
- SSE 断线、取消、重连和超时；
- 小程序端构建、页面交互和真机网络条件；
- 生成质量回归集、成本/延迟预算。

建议将“静态检查、单元测试、API 合约测试、生成离线回放测试、端到端测试、依赖审计”拆成独立 CI 阶段，并固定依赖锁文件或可复现环境。

| 顶层导航 | 5 个：书架、开卷、追风、落笔、付梓 |
| 按钮 | 约 112 |
| 输入控件 | 约 46（input/textarea/select） |

页面采用侧栏和 PWA 结构，且 viewport 设置了 `user-scalable=no`，不符合小屏设备的可访问性取向。当前不是“按钮颜色需要调整”，而是信息架构和状态模型需要重建。

### 6.2 重复或应该降级的功能

| 当前功能 | 问题 | 改造建议 |
|---|---|---|
| 创建页与写作页都提供“AI 修改大纲” | 同一动作在两个场景重复暴露 | 保留一个“调整大纲”入口，写作页只提供章节级修改 |
| “拆解需求 / 监督质量 / 循环校验 / 追加需求” | 用户难以理解区别，多个按钮实际作用重叠 | 合并为一个“需求与质量”向导，默认自动执行，高级页查看结果 |
| 标准模式/原子模式 | 将实现策略暴露为产品概念 | 默认由服务端选择，专家模式再开放 |
| 互动自动/手动、语音开关、情绪音、角色声音 | 多个开关互相影响，移动端操作成本高 | 合并为“剧情推进”和“朗读设置”两个二级设置 |
| 剧情图谱 8 个标签页 | 信息密度过高，移动端难以定位 | 首屏只保留摘要、人物、伏笔；其余进入详情页 |
| 追风/小红书/趋势生成 | 与小说主流程是另一条产品线 | MVP 移出主导航，作为“工具箱”或后续版本 |
| 多种导出按钮 | TXT/PDF/批量导出并列，且可能触发长任务 | 统一为“导出”任务页，完成后通知下载 |

### 6.3 建议的新信息架构

```text
书架
 ├─ 最近阅读/生成中/草稿
 └─ 搜索、归档、删除

创建
 ├─ 1 灵感：一句话或一段需求
 ├─ 2 设定：题材、基调、篇幅、风格属性
 └─ 3 大纲：预览、编辑、确认

写作
 ├─ 当前章节阅读与编辑
 ├─ 生成进度/暂停/继续/重试
 ├─ 下一步建议
 └─ 更多：人物、伏笔、剧情图谱、互动、质量报告

我的
 ├─ 生成额度与历史任务
 ├─ 朗读/显示/通知设置
 ├─ 隐私、内容管理、导出与注销
 └─ 帮助与反馈
```

核心原则是“一页一个主动作”：创建页的主动作是“确认大纲”，写作页的主动作是“生成下一章/继续生成”，阅读页的主动作是“继续阅读”。

### 6.4 小程序端交互要求

- 以 375/414 宽度、刘海安全区和弱网为基线；点击目标建议不小于 44 px。
- 不依赖浏览器 DOM、Service Worker、localStorage 或 PWA manifest；使用 WXML/WXSS/JS/TS、`wx.request` 和小程序生命周期。
- 生成任务必须可离开页面后继续，并可从书架恢复；不能把 SSE 连接等同于任务本身。
- 流式展示、轮询或 WebSocket 方案需要在微信开发者工具和真机上验证；接口域名、TLS、隐私授权和内容审核流程以微信后台及官方文档的当期要求为准。
- 首屏只加载书架摘要，不拉取整本小说；章节分页、草稿本地暂存、失败重试和断线恢复必须是明确状态。

## 7. 生成质量审计

### 7.1 当前链路优点

- 有大纲、章节、角色状态、共享记忆、剧情图谱、反馈和合规检查等多层结构。
- 原子化生成尝试用 beat 拆分改善长章节结构。
- 有 PacingChecker、Humanizer、连贯性/逻辑检查和大纲合规报告。
- 已有批量生成检查点、生成锁和部分状态落盘设计，方向是对的。

### 7.2 质量风险

#### P1-Q-01：上下文裁剪可能优先丢失当前章节大纲

上下文拼装以字符长度近似 token 预算，并从尾部移除内容。当前章节大纲在一组较早的上下文片段中，可能在预算压力下被移除，而低优先级信息先前已经进入 prompt。生成器因此可能写出语言流畅但不执行本章任务的内容。

**建议：**改成带优先级的 token 预算器：当前章节硬约束/核心事件 > 角色状态/上一章摘要 > 伏笔和世界观 > 风格和可选增强；每次请求记录实际 token 与被裁剪的字段。

#### P1-Q-02：规则分数不等于文学质量

PacingChecker、钩子关键词、短句比例、对白比例等规则适合发现异常，不适合单独决定“重写”。当前质量门在部分分数区间存在自动重写或放行，可能造成误杀，也可能放过结构性问题。

**建议：**先执行硬约束检查（章节目标、人物、核心事件、禁写项、截断），再用结构化语义评审做二次判断；自动重写必须保留原稿、原因、前后评分和用户撤销入口。

#### P1-Q-03：大纲补写后没有完整质量回归

原子化/标准化生成都会执行大纲合规步骤。补写文本追加到全文并保存，但前序质量/连贯性评估可能已经完成，补写后的全文没有强制重新经过完整评估。这样会出现“合规分数提高，但语言、节奏或重复度变差”的情况。

**建议：**把管线固定为“草稿 → 硬约束 → 合规修补 → 全文最终评估 → 版本提交”，任何修改都生成新版本，禁止在旧评估结果上直接宣称最终通过。

#### P1-Q-04：原子化生成成本和一致性风险高

每 beat 多候选会增加调用次数和成本；候选选择主要依赖启发式评分，并带随机选择，不是完整的角色状态、因果和跨 beat 语义重排。它可能提升局部新鲜感，同时损害整章声音和因果。

**建议：**默认单候选或少量候选；只有检测到高风险章节才开启多候选。候选必须经过结构化状态变化、人物出场、事件因果和重复度评分，再由可解释的 rerank 选择。保存随机种子和模型参数，保证问题可复现。

#### P1-Q-05：失败占位内容可能落盘

Beat 生成失败时存在 `（生成失败 - beat）` 类占位文本路径。生成任务必须在任何占位、错误、截断或未闭合结构出现时进入 `failed/needs_review`，不能把失败字符串作为正常章节发布。

#### P1-Q-06：模型调用存在同步阻塞

`backend/core/mixins/generation.py:499` 和 `:1068` 有异步生成流程中的直接同步 LLM 调用；`resilient_client.py:202-217` 虽将建连放入线程，但随后在异步生成器内同步迭代响应。长流或重试会阻塞事件循环，表现为同进程其他用户请求变慢。

**建议：**统一 LLM adapter，所有同步 SDK 调用、流迭代、退避和取消都在线程/异步客户端边界内完成；生成任务放入队列，HTTP 层只消费任务事件。

### 7.3 生成质量指标

改造后不应只看“生成成功率”。建议建立固定评测集和以下指标：

| 指标 | 目标用途 |
|---|---|
| 大纲核心事件命中率 | 判断章节是否真正执行计划 |
| 人物状态连续性错误率 | 检测角色能力、关系、位置和知识矛盾 |
| 伏笔保持/回收率 | 衡量长篇记忆质量 |
| 章节人工可读通过率 | 防止规则分数冒充文学质量 |
| 重写误杀率 | 评估质量门是否破坏合格文本 |
| 生成成功/恢复率 | 衡量弱网、断线、取消后的体验 |
| 平均耗时、P95 耗时 | 设计用户等待和任务通知 |
| 每章 token/成本 | 设定配额和模型路由 |
| 失败占位落盘数 | 应为 0 |

## 8. 目标架构建议

### 8.1 推荐目标形态

```text
原生微信小程序
  ├─ 登录/隐私授权
  ├─ 书架与作品状态
  ├─ 创建向导
  ├─ 大纲确认
  ├─ 章节阅读/编辑
  └─ 任务进度/通知
          │ HTTPS
          ▼
API 层（认证、权限、schema、限流、幂等）
          ▼
作品域服务 + 生成任务服务
  ├─ Planner
  ├─ Writer
  ├─ Quality Gate
  └─ Export/Moderation
          │
          ├─ 关系数据库：用户、作品、版本、任务、用量、反馈
          ├─ 对象存储：章节、导出文件、版本快照
          ├─ 任务队列：生成、评估、导出、通知
          └─ LLM Adapter：超时、重试、成本、模型路由、审计
```

### 8.2 数据实体最小集合

- `users`：内部 user_id、微信标识哈希/加密字段、状态、创建/注销时间。
- `novels`：owner_id、标题、类型、状态、当前版本、软删除时间。
- `outlines`：作品版本、结构化大纲、编辑者、确认状态。
- `chapters`：章节版本、草稿/最终状态、正文对象地址、摘要、质量报告。
- `generation_jobs`：任务类型、状态、进度、幂等键、取消时间、错误码、成本。
- `feedback`：作品/章节/版本关联、用户反馈、是否已用于后续偏好。
- `usage_ledger`：用户/作品/任务的 token、模型、费用估算、配额扣减。
- `audit_events`：登录、访问、导出、删除、审核、管理员操作。

### 8.3 API 形态

建议把现有按“调用后等待结果”的接口逐步改为：

```text
POST   /v1/novels                         创建作品
GET    /v1/novels                         分页书架摘要
GET    /v1/novels/{id}                    作品详情
POST   /v1/novels/{id}/outline/jobs       创建大纲任务
POST   /v1/novels/{id}/chapter/jobs       创建章节任务
GET    /v1/jobs/{job_id}                  查询任务状态
POST   /v1/jobs/{job_id}/cancel           取消任务
GET    /v1/jobs/{job_id}/events           获取进度事件
GET    /v1/novels/{id}/chapters/{n}       分页读取章节
POST   /v1/chapters/{id}/revisions        保存新版本
POST   /v1/exports                        创建导出任务
```

每个写操作带 `Idempotency-Key`；所有接口在认证后再执行 owner_id 过滤。事件通道可以先用短轮询验证闭环，再根据真机表现选 WebSocket 或其他适配方式。

## 9. 分阶段改造计划

### Phase 0：上线安全冻结

目标：先让系统不具备明显的公开越权和无限消耗风险。

- 统一 UUID/路径安全函数和全路由鉴权依赖。
- 移除公开健康接口的路径/作品信息。
- 把所有裸 `dict` 请求体改为有限制的 schema。
- 加入内容输入长度、章节范围、模型 token、并发、超时和每日额度。
- 修复批量检查点缺陷、健康检查脚本和 backend 依赖清单。
- 建立 API 安全回归测试和依赖锁定策略。

**出口标准：**路径穿越、未授权访问、跨用户读取/写入、无限生成四类测试全部失败闭环；没有高危默认配置。

### Phase 1：后端多租户与任务化

- 引入数据库实体和迁移。
- 将本地文件访问封装为 repository/object storage 接口。
- 把章节生成、批量生成、导出、质量检查改为持久化 job。
- 统一 LLM adapter，记录模型、token、耗时、重试和成本。
- 支持断线恢复、取消、重试、失败状态和版本回滚。

**出口标准：**两个服务实例并行时任务与数据仍一致；用户只能看到自己的作品；同一幂等键不会重复扣费或重复生成。

### Phase 2：原生小程序 MVP

- 创建 `app.json`、页面、组件、主题变量和统一请求层。
- 首版只做：登录/隐私、书架、创建向导、大纲确认、章节生成、阅读/编辑、任务恢复、导出。
- 将趋势、小红书、互动、剧情图谱、语音和质量实验室移到“更多”或暂不迁移。
- 用真实小程序开发者工具和真机验证弱网、后台恢复、长文本滚动和分享链路。

**出口标准：**新用户在 3 分钟内能创建作品并发起第一章；生成中离开页面后可从书架恢复；失败可重试且不会生成重复章节。

### Phase 3：生成质量重构

- 建立结构化大纲、故事圣经、角色状态和事件日志。
- 改造 token 预算器，保证当前章节大纲和硬约束不被裁剪。
- 合并质量门和大纲合规流程，补写后重新评估并提交新版本。
- 建立离线回归集、人工评分和模型/参数对照实验。
- 将作者名风格改为属性化风格卡。

**出口标准：**每次质量改造都有前后评测；质量、成本、延迟三个维度不能以牺牲另外两个为代价而无记录上线。

### Phase 4：高级能力迁移

- 互动模式：先实现事件驱动的剧情分支和可恢复状态，再接语音。
- 剧情图谱：先做摘要、人物、伏笔三个移动端高频视图。
- 趋势/小红书：作为独立工具域，单独设计审核、版权和分享权限。
- 导出：异步任务、临时链接、权限与过期策略。

## 11. 结论与下一步

### 结论

当前项目的核心价值在“生成能力栈已经丰富”，而不是“已经是一个可直接上线的产品”。最重要的工作顺序应是：

```text
安全隔离与任务模型
        ↓
小程序核心闭环
        ↓
生成质量可测量化
        ↓
高级功能迁移与视觉升级
```

如果反过来先重绘现有大页面，最终会把未解决的身份、存储、任务和成本问题搬到移动端，既增加工作量，也无法降低上线风险。

### 建议下一次实施任务

1. 先实现服务端统一资源校验、认证占位接口、`novel_id` 路径安全和 P0 API 测试。
2. 再把生成接口抽象为 `generation_jobs`，保留现有生成核心作为 worker，避免一次性重写全部生成算法。
3. 同时建立原生小程序骨架和 4 个主页面，只接书架—创建—大纲—写作闭环。
4. 最后根据固定评测集改造上下文预算、质量门和原子化候选策略。

本报告作为后续改造的基线。后续任何“已修复”结论都应同时附源码位置、测试命令和前后指标，不能只依据旧版项目状态报告或 UI 能否打开来判断完成。
