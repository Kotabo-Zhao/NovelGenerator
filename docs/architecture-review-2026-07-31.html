核心结论：骨架合理，但已到「巨石化」拐点

架构骨架是健康的 —— 多智能体编排 + 分层记忆 + 韧性客户端 三层设计抓住了 AI 创作类应用的本质问题（上下文管理、失败降级、质量门控），23 个 Agent 职责清晰、技能模块低耦合。当前最主要的架构风险不在「层」而在「块」：engine / server / 前端 index.html 三块巨石文件 + 双份 Python 副本靠人肉同步，正在吃掉前 6 个版本迭代积累的可维护性红利。结论：架构与当前个人工具定位匹配，可继续演进；但任何「团队化、商业化、多实例部署」的下一步动作前，必须优先处理巨石拆分与副本同步自动化。

✅ 多智能体编排合理 ✅ 分层记忆成熟 ✅ 韧性/降级设计突出 ⚠️ 三块巨石文件 ⚠️ 副本同步靠人肉 ⚠️ 测试无法本地跑全

1架构总览

四层纵向分层 + 三端横向部署。前端 / API / 编排 / 数据 各司其职，DeepSeek 为唯一外部依赖。
核心层 支撑模块 共 40 个 core 模块 · 23 个 Agent · 71 个 API

2分层与模块化 — 骨架健康

核心结论：四层依赖方向基本单向、技能模块解耦良好；但编排层出现「上帝类」，API 层与前端层巨石化。

✅ 依赖方向清晰

  • API → Engine → 领域 Agent → SharedMemory → ResilientClient，逐层向下
  • 19 个技能模块只依赖 resilient_client，扇入/扇出结构健康
  • reusable_client 隔离 LLM 细节（重试/退避/续传），上层完全无感

✅ 模块粒度合理

  • 每个 Agent 一个文件、单一职责（Planner 管大纲、Writer 管正文、PacingChecker 管节奏）
  • 新增 Agent = 新增文件 + engine 注入，扩展成本低（历史上已叠加到 23 个）
  • v2.x 迭代通过「加模块」而非「改核心」推进，架构韧性受益于此

⚠️ 编排层上帝类

  • engine.py 2199 行 / 40+ 方法 / 依赖 26+ 模块
  • 导出 EPUB、POV 检测、角色宝典、锁管理等「非编排」逻辑都堆在 Engine
  • 任何模块改动都要触碰 engine，回归面大

3核心数据流 — 两遍式设计成熟

创作管线与写作管线均为「分阶段 + 强降级」设计，信息逐层沉淀到磁盘文件，可断点续跑。

创作管线（create_novel_stream）

# Phase 0 需求拆解 灵感 → RequirementDecomposer → 12-25 条子任务 # Phase 1-3 大纲生成 → Planner.plan_stream（世界观→角色→分卷→逐章） # 落盘（原子写） → plan.json + character_bible.json → storygraph.json + arcs + foreshadowing.json → novel_state.json（进度状态） # 失败策略 每个非核心步骤 try/except 降级 → 不阻断主线

写作管线（generate / atomic 双轨）

# 上下文组装（5 层） shared_memory.build_writer_context （核心设定/桥接/摘要/状态/伏笔/大纲） # 两遍式写作 ① Writer 初稿（元指令提至 system） ② 独立结尾生成（章末钩子保护） # 质量门 PacingCheck → AI 检测 → Humanizer # 原子化路径（v2.3 双轨） Blueprint → BeatDecomposer → 逐 beat LLM → BeatAssembler（去重/平滑/评估） # 沉淀 chapter_XXXX.md + 状态/伏笔/图谱更新

双轨制说明（架构上需要正视）

系统内存在两条并行的章节生成路径：普通 Writer 路径（1 次 LLM 调用整章）与原子化路径（5-7 次 LLM 调用逐 beat）。README 与 AUDIT_REPORT（P1-1）均指出两条路径产出质量差异大（普通路径趋同、原子路径连贯性差）。双轨并存导致：同一功能两套实现、两套调参、两套 bug 面。当前默认启用原子化，但普通路径代码并未移除 —— 建议尽快收敛为单一主路径。

4多端架构 — 三副本同步机制是双刃剑

PC Web（Render）+ Android APK（Chaquopy 内嵌 Python）+ XHS Worker（Docker）三端，共享同一套 core 代码。

副本拓扑

代码副本数同步方式
core/*.py（40 文件）2 份（backend + android）tools/sync_android_core.py（人肉触发）
前端（index.html 等）3 份（web + backend/web + android/web）tools/sync_frontend.py（人肉触发）
api/server.py2 份（平台差异版本）各自维护（CORS/WEB_DIR 不同）

当前一致性良好：core 40 文件 md5 全等、前端三副本 md5 全等、server.py 仅 5 行平台差异。同步脚本设计专业（--check 模式 + 差异报告）。

风险：同步依赖人肉纪律

  • 实测发现：git 提交「CORS 锁定域名」只同步到了 Android 副本，backend 主副本仍是 allow_origins=["*"] + allow_credentials=True——同一处 bug 修了 A 端漏了 B 端
  • CI（.github/workflows/ci.yml）只做语法检查 + 密钥扫描，不校验三副本一致性——不一致可以静默合入 main
  • Android 使用 Chaquopy 内嵌整套 Python（24,000 行）打包进 APK：包体积大、版本漂移风险高
  • 替代方向：Android 改为「远程 API 客户端」或「core 子集裁剪」，但工程量大，现阶段维持副本+CI 校验是可接受方案

6问题清单

按影响面与修复成本分级。P0 = 立即修，P1 = 1-2 周，P2 = 规划内。

🔴 P0 — 隐藏 bug 与一致性缺口

级别问题证据 / 影响
P0死引用 NovelPlannerserver.py:1841 引用 from core.planner import NovelPlanner，该类在 backend 与 android 两个副本中均不存在（已 AST 验证）。POST /api/trends/bizarre/create 一旦走到该分支必然 500。端点为新功能，未被主流程覆盖 → 静默坏点。
P0CI 不校验三副本一致性ci.yml 仅 py_compile + 密钥扫描。已实测发生「CORS 修复只进 Android 副本」的漂移。不一致代码可无感合入 main，是结构性隐患而非一次性失误。
P0测试套件本地跑不通tests/test_suite.py 全量运行时在 TestPlannerStream 处卡死（超时 9 分钟无输出）。前 38 个测试全过（PlannerJSON/AtomicIO/Writer/Memory），asyncio 相关测试无法回归。已知还有 2 个预存失败。
P0CORS 配置脱节backend/server.py 硬编码 allow_origins=["*"] + allow_credentials=True（无效且危险组合），与 config.py 的 CORS_ORIGINS 完全脱节；Android 副本已改用配置。部署到 Render 后为开放跨域。

🟡 P1 — 架构演进阻碍

级别问题证据 / 影响
P1engine.py 上帝类2199 行 / 40+ 方法 / 依赖 26+ 模块。编排 + 具体实现（EPUB 导出、POV 检测、锁管理、角色宝典）混杂，单文件回归面过大。
P1server.py 巨石文件2048 行 / 71 路由无 APIRouter 分组、无依赖注入、无请求模型复用（dict 满天飞，git log 有「FastAPI body parsing」修复记录）。
P1前端单文件巨石index.html 3718 行 / 224 函数 / 86 个 ref 状态 / 无组件化 / 无构建链 / 无类型检查 / 手写视图切换（v-if）。改一处可能碰全局。
P1进程内可变状态engine._requirements 为内存 dict（代码注释自认「PENDING: needs DB migration for multi-process」）；rate limit 为内存 defaultdict。多 worker / 多进程部署即失效。
P1双轨生成未收敛普通 Writer 路径与原子化路径并存，AUDIT P1-1 已指出质量差异。两套路径两套 bug 面。
P1async 中同步阻塞planner.py _call_llm 使用 time.sleep(attempt+1)（同步退避）阻塞事件循环；大段同步 LLM 调用依赖 asyncio.to_thread 手工包裹。并发场景响应性差。

级别问题说明

7值得保留的架构资产

以下设计经得起检验，后续重构时必须保留、不要破坏。

🛡️ 韧性优先的设计哲学

  • ResilientLLMClient：重试/退避/断点续传，LLM 调用全部走统一抽象
  • 四级 JSON 降级：validate → repair → parse_partial → force_extract，LLM 输出畸形 JSON 也不会挂流程
  • 非核心步骤全部 try/except 降级：图谱初始化失败不阻断大纲生成
  • 原子写入（atomic_io）：损坏文件自动恢复，"章节 .md 在磁盘上就永不丢失"是正确原则

🧠 分层记忆架构（L1/L2/L3）

  • 核心设定 / 近期上下文 / 伏笔追踪三层隔离，prompt 组装按需拼接
  • SharedMemoryManager 统一缓存 + 乐观锁 + 订阅通知，接口一致性好
  • memory.py 薄包装层保持向后兼容，v2.1 迁移无破坏
  • 渐进式摘要压缩（check_and_compress）控制长篇小说上下文膨胀

🤖 多智能体职责划分

  • 创作（Planner/Writer/Beat）、拆解（Requirement/Feedback）、质量（Pacing/Humanizer/Consistency）、追踪（StoryGraph/ArcPlanner）四类 Agent 边界清晰
  • 新增能力 = 新增文件 + Engine 注入，历史已验证可扩展到 23 个

🔧 同步工具工程化

  • sync_frontend.py / sync_android_core.py 支持 --check 模式，可作为 CI gate 直接接入
  • Android 平台差异（CORS、WEB_DIR）用 server.py 独立维护，core 保持 1:1

8改进路线图

按「先止血、再拆墙、后升级」排序，每步都给出明确的完成判据。
STEP 1 · 止血（1-2 天）
修掉三个静默坏点
  • 删除或实现 NovelPlanner 死引用（/api/trends/bizarre/create 返回 500 的根因）
  • backend/server.py 的 CORS 改为读取 config.CORS_ORIGINS（对齐 Android 副本）
  • 定位 test_suite 卡死根因（TestPlannerStream 的 asyncio/同步退避问题），恢复本地全量回归
STEP 2 · CI 上锁（半天）
把副本一致性变成机器检查
  • ci.yml 增加步骤：跑 sync_frontend.py --check + sync_android_core.py --check，不一致即 CI 失败
  • ci.yml 增加 pytest（至少 test_suite 前 38 项 + resilient 21 项）
  • 判据：main 分支永远满足「三副本一致 + 核心测试绿」
STEP 3 · 拆巨石（1-2 周）
把三块巨石切成有边界的模块
  • server.py：按域拆 APIRouter（novels / outline / quality / storygraph / requirements / styles / xhs），每域一文件，共用请求模型
  • engine.py：抽出导出（ExportService）、校验（ValidationService）、状态（GenerationCoordinator），Engine 只留编排
  • index.html：先按视图拆为多文件（shelf.js / create.js / write.js / storygraph.js / export.js），用构建脚本拼接（不引入 Vite 也可），后续再升级组件化
STEP 4 · 状态与并发升级（规划期）
为多实例部署做准备
  • _requirements 等进程内状态迁移 SQLite（代码注释已指明方向）
  • rate limit 换 Redis 或接受单 worker 部署约束（Render 免费版本为单实例，当前可接受）
  • 文件锁换 threading.Lock + 跨进程语义（portalocker），去掉 300s 兜底依赖
  • 生成路径收敛：原子化为主，普通路径降级为 fallback 或移除
STEP 5 · 升级（商业化前置）
团队化 / 公网部署前必须项
  • 鉴权 + 内容审核 + API key 托管（AUDIT Phase 4 清单）
  • 结构化日志 + 生成成功率/耗时指标
  • 前端引入类型检查（TS 或 JSDoc）+ 组件化重构
